# מדריך: גיבוי ושחזור של המערכת

המדריך הזה מתאר את מנגנון הגיבוי והשחזור כפי שהוא ממומש ב-TaskFlow, בצורה
שמאפשרת להעתיק אותו לפרויקט אחר. הוא לא מסמך תפעול ("איפה לוחצים") — הוא הסבר
על ההחלטות, הקוד שמממש אותן, והמלכודות שכל אחת מהן פותרת.

הנחות הבסיס של המימוש: אפליקציית FastAPI אסינכרונית, MongoDB דרך motor,
דיפלוי על Render עם דיסק מתמיד. אם הסטאק שלכם שונה — רוב הרעיונות עדיין
תקפים, ואני מסמן במפורש איפה משהו קשור לפלטפורמה.

---

## ההחלטה הראשונה: בלי mongodump

הרפלקס הרגיל לגיבוי Mongo הוא `mongodump` בתוך cron. זה עובד יופי בשרת שאתם
מנהלים. זה נשבר בדיוק ברגע שאתם עוברים לפלטפורמת PaaS: `mongodump` הוא חלק
מ-`mongodb-database-tools`, חבילה שצריך להתקין בנפרד, בגרסה שתואמת לשרת,
ולוודא שהיא שורדת כל rebuild. ב-Render זה אומר build command מותאם או Dockerfile
במקום runtime פשוט.

המימוש כאן עושה את זה אחרת: שולף את כל המסמכים דרך אותו driver שהאפליקציה כבר
משתמשת בו (motor), ומסדר אותם בקובץ zip. אפס תלויות חדשות. הקוד כולו ב-
`app/core/backup.py`.

התמורה על ההחלטה הזאת היא אמיתית ושווה להכיר אותה: `mongodump` מייצר BSON גולמי,
מגבה גם אינדקסים, ויודע לעבוד ב-streaming. המימוש הפייתוני מגבה מסמכים בלבד,
טוען כל collection לזיכרון, וסומך על כך שהאינדקסים נוצרים מחדש בקוד. בפרויקט
עם מסד של מאות מגה — זו תמורה מצוינת. בפרויקט עם עשרות ג'יגה — תשתמשו
ב-`mongodump`.

הטעות הנפוצה כאן: לבחור בכלי החיצוני "כי זה הסטנדרט", ואז לגלות חצי שנה אחרי
הדיפלוי שהגיבוי שקט כבר שלושה חודשים כי rebuild הרג את ההתקנה. הסימפטום:
אף אחד לא יודע מתי רץ הגיבוי האחרון. הפתרון: לגבות בקוד של האפליקציה עצמה,
כך שאם האפליקציה עלתה — הגיבוי עובד.

## פורמט הארכיון

כל גיבוי הוא קובץ zip יחיד:

```
backup_2026-05-03_03-00-15.zip
├── _meta.json          (גרסת פורמט, תאריך, שם המסד, ספירת רשומות לכל collection)
├── clients.json
├── projects.json
├── tasks.json
└── ...
```

שלוש החלטות מסתתרות פה.

**zip ולא tar.gz.** אותה דחיסה בדיוק (DEFLATE), אבל כל מערכת הפעלה פותחת zip
בקליק כפול. זה נשמע קוסמטי עד הפעם הראשונה שאתם צריכים לענות על "האם הלקוח
הזה היה במערכת בשבוע שעבר?" — עם zip פותחים, מציצים ב-`clients.json`, סוגרים.
בלי לשחזר כלום, בלי מסד זמני.

**Extended JSON v2 ולא JSON רגיל.** JSON רגיל לא יודע לייצג `ObjectId`,
`datetime` או `Decimal128`. אם תדחפו `json.dumps` על מסמך Mongo תקבלו
`TypeError`, ואם תעקפו את זה עם `default=str` — תקבלו גיבוי שמשחזר את התאריכים
כמחרוזות ואת המזהים כטקסט. הפורמט של `bson.json_util` שומר את הטיפוסים:

```json
{"_id": {"$oid": "6634..."}, "created_at": {"$date": "2026-05-03T09:00:00Z"}}
```

`json_util.loads` מחזיר את זה בדיוק לטיפוסים המקוריים. זה מה שהופך את הגיבוי
לשחזור אמיתי ולא לייצוא נתונים.

**`_meta.json` נכתב אחרון.** הוא מכיל את ספירת הרשומות לכל collection, ואת
הספירות יודעים רק אחרי שכתבו את כולן. הוא גם מכיל `format_version` — כדי
שאם תשנו את המבנה בעתיד, סקריפט השחזור יוכל להבחין בין הפורמטים במקום
להתרסק על גיבוי ישן.

## לב הגיבוי

השליפה עצמה פשוטה:

```python
async def _dump_collection_to_string(db, coll_name: str) -> tuple[str, int]:
    docs = []
    cursor = db[coll_name].find({})
    async for doc in cursor:
        docs.append(doc)
    return json_util.dumps(docs, indent=2, ensure_ascii=False), len(docs)
```

`ensure_ascii=False` הוא לא פרט טכני — בלעדיו כל טקסט עברי במסד נשמר כרצף
`אב` וקובץ הגיבוי הופך לבלתי קריא לעין אנושית. עם הדגל, פותחים את
`tasks.json` ורואים את שמות המשימות.

הכתיבה לקובץ היא החלק שבו מסתתר הבאג הקלאסי:

```python
tmp_path = target_path.with_name(target_path.name + ".partial")
try:
    with zipfile.ZipFile(tmp_path, "w", zipfile.ZIP_DEFLATED, compresslevel=6) as zf:
        for coll_name in collections:
            json_str, doc_count = await _dump_collection_to_string(db, coll_name)
            zf.writestr(f"{coll_name}.json", json_str)
            meta["collections"][coll_name] = doc_count
        zf.writestr("_meta.json", json.dumps(meta, indent=2, ensure_ascii=False))
    tmp_path.replace(target_path)
except Exception:
    if tmp_path.exists():
        try:
            tmp_path.unlink()
        except OSError:
            pass
    raise
```

ה-`try` הפנימי אינו קישוט: אם המחיקה עצמה נכשלת (הרשאות, דיסק מלא), חריגת
הניקוי הייתה מחליפה את שגיאת הגיבוי המקורית ובלוג הייתם רואים "לא ניתן למחוק
קובץ" במקום הסיבה האמיתית לכישלון.

כותבים ל-`.partial`, ורק אחרי שהקובץ נסגר בהצלחה עושים `replace` — פעולה אטומית
ברמת מערכת הקבצים. בלי זה, אם השרת נפל באמצע הכתיבה, נשאר בתיקייה קובץ בשם
`backup_2026-05-03_03-00-15.zip` שנראה תקין ברשימה, נספר ברוטציה, ומתגלה כחצי
קובץ בדיוק ביום שבו אתם צריכים אותו. שורה אחת של קוד מבטלת את התרחיש הזה לגמרי.

שימו לב גם ל-`sorted(await db.list_collection_names())` — הגיבוי מגלה את
ה-collections בזמן ריצה ולא מקבל רשימה קשיחה. הוספתם collection חדש למערכת?
הוא מגובה מהיום הראשון בלי שנגעתם בקוד הגיבוי.

## מניעת ריצות מקבילות

יש שני מקורות שיכולים להפעיל גיבוי: ה-scheduler היומי, וכפתור "גיבוי עכשיו"
במסך הניהול. אם שניהם יורים באותה שנייה, שתי ריצות שולפות במקביל את כל המסד
ועלולות לכתוב לאותו שם קובץ.

הפתרון הוא `asyncio.Lock` ברמת המודול, אבל עם טוויסט:

```python
_backup_lock = asyncio.Lock()

async def run_backup() -> BackupResult:
    if _backup_lock.locked():
        return BackupResult(success=False, error=BACKUP_ALREADY_RUNNING_ERROR, ...)
    async with _backup_lock:
        try:
            return await _run_backup_locked()
        except Exception as exc:
            ...
```

הבדיקה `if _backup_lock.locked()` לפני ה-`async with` היא העיקר. בלעדיה, לחיצה
על הכפתור בזמן שגיבוי רץ הייתה *ממתינה* לסיום ואז מריצה גיבוי שני — בקשת HTTP
שתקועה שתי דקות ומייצרת עבודה מיותרת. עם הבדיקה, הקריאה חוזרת מיד עם שגיאה
ברורה, וה-router מתרגם אותה ל-409:

```python
if result.error == BACKUP_ALREADY_RUNNING_ERROR:
    raise HTTPException(status_code=409, detail=result.error)
raise HTTPException(status_code=500, detail=result.error or "הגיבוי נכשל")
```

ההבחנה בין 409 ל-500 היא ההבדל בין "תפוס, נסה עוד רגע" לבין "משהו נשבר, לך
לבדוק". שני מצבים שונים לגמרי מבחינת המשתמש — ובלי ההבחנה הזאת שניהם נראים
כמו "הגיבוי נכשל".

ה-`try/except` הרחב סביב הלוגיקה הוא רשת ביטחון מכוונת: `run_backup` לעולם לא
זורקת חריגה. ה-scheduler קורא לה, וקריאה שזורקת עלולה להפיל job ולהשאיר את
המערכת בלי גיבויים בשקט. במקום זה, כל כישלון מוחזר כאובייקט `BackupResult`
עם `success=False` ונרשם ב-log.

**מגבלה שחשוב להכיר:** הנעילה היא בתוך תהליך. אם תריצו כמה worker processes
(gunicorn עם `-w 4`), לכל אחד יש lock משלו ו-scheduler משלו — ותקבלו ארבעה
גיבויים מקבילים. TaskFlow רץ ב-worker יחיד ולכן זה לא רלוונטי לו. אם הפרויקט
שלכם רץ במספר workers, צריך נעילה מבוזרת (למשל מסמך `backup_lock` ב-Mongo עם
TTL, או להריץ את ה-scheduler בשירות נפרד).

## רוטציה: לפי mtime, לא לפי השם

```python
def rotate_backups(retention_days: int) -> list[str]:
    if retention_days <= 0:
        return []
    cutoff_ts = datetime.now(timezone.utc).timestamp() - (retention_days * 86400)
    ...
```

מפתה לפרסר את התאריך משם הקובץ — הוא הרי כתוב שם. אל תעשו את זה. שם הקובץ הוא
מחרוזת שאפשר לזייף, לשנות ידנית, או להעתיק בטעות, ופרסינג שלו הוא נקודת כישלון
נוספת. `mtime` הוא נתון של מערכת הקבצים שמשקף את מה שקרה בפועל.

הרוטציה נקראת מתוך `_run_backup_locked` אחרי גיבוי מוצלח, ועטופה ב-`try/except`
משלה — כישלון במחיקת קובץ ישן לא הופך גיבוי מוצלח לכושל. הסדר הזה חשוב: קודם
מגבים, ורק אחר כך מוחקים ישנים. אם תעשו את זה הפוך, גיבוי שנכשל אחרי שהרוטציה
כבר רצה משאיר אתכם עם פחות גיבויים ממה שהתחלתם.

## תזמון

APScheduler רץ בתוך תהליך האפליקציה, נטען מה-lifespan של FastAPI:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    await connect_to_mongo()
    start_scheduler()
    yield
    stop_scheduler()
    await close_mongo_connection()
```

ההגדרה של ה-job:

```python
_scheduler.add_job(
    _backup_job,
    trigger=CronTrigger(hour=settings.backup_hour, minute=settings.backup_minute, timezone="UTC"),
    id=BACKUP_JOB_ID,
    replace_existing=True,
    misfire_grace_time=3600,
    coalesce=True,
    max_instances=1,
)
```

שלוש השורות האחרונות הן מה שמפריד בין scheduler שמתנהג יפה לבין כזה שמפתיע
אתכם. `max_instances=1` מונע ריצה שנייה בזמן שהראשונה עוד עובדת.

שתי האחרות עובדות ביחד, ושווה לדייק בהן כי קל לתאר אותן לא נכון.
`misfire_grace_time=3600` הוא **חלון**: הרצה שהוחמצה תבוצע רק אם היא מאחרת
בפחות משעה. הרצה שאיחרה יותר נחשבת misfire ומדולגת — לא מורצת רטרואקטיבית
בשעה אקראית. `coalesce=True` פועל **בתוך** החלון הזה: אם כמה הרצות ממתינות
בו-זמנית, הן מתאחדות לאחת במקום להצטבר.

מכאן שאם השרת היה כבוי יומיים, לא יקרה כלום — כל ההרצות שהוחמצו מחוץ לחלון
פשוט נופלות, והגיבוי הבא הוא זה המתוזמן הרגיל. `coalesce` לא מציל אתכם שם;
הוא רשת ביטחון לתקלה קצרה, כמו deploy שהתארך.

שימו לב לניואנס באזורי זמן: ה-scheduler מוגדר `timezone="UTC"` וגם הטריגר.
זה מכוון — גיבוי ב-03:00 UTC רץ תמיד באותו רגע בשנה, בלי לזוז שעה קדימה ואחורה
עם שעון קיץ. תזכורות שפונות למשתמש הן סיפור אחר; ב-TaskFlow תזכורות השותף
משתמשות ב-`timezone=settings.partner_timezone` בדיוק מהסיבה ההפוכה — "20:00"
בשביל בן אדם צריך להיות 20:00 אצלו.

עוד פרט קטן ששווה להעתיק: ה-scheduler בכלל לא עולה אם אין לו jobs פעילים.

```python
if not backup_active and not telegram_active and not partner_active:
    logger.info("אין jobs פעילים - לא מתזמן")
    return
```

## איפה הקבצים חיים — המלכודת הגדולה

זו הנקודה שבה גיבויים נכשלים בשקט על פלטפורמות PaaS, ולכן היא ראויה למקום משלה.

מערכת הקבצים של Render (וגם של Heroku, Fly, Cloud Run וכל השאר) היא **ארעית**.
כל דיפלוי, כל restart, כל מעבר של הקונטיינר למכונה אחרת — מוחק הכל. אפשר לכתוב
גיבוי מושלם ל-`/app/backups`, לראות אותו ברשימה, ולגלות שהוא נעלם אחרי הדחיפה
הבאה לריפו.

הפתרון הוא Persistent Disk, מוגדר ב-`render.yaml`:

```yaml
services:
  - type: web
    name: taskflow
    plan: starter          # דיסק מתמיד לא קיים ב-free
    disk:
      name: taskflow-backups
      mountPath: /var/data
      sizeGB: 1
    envVars:
      - key: BACKUP_DIR
        value: /var/data/backups
```

שני דברים לשים לב אליהם. ראשית, זה דורש תוכנית בתשלום — במסלול החינמי אין
דיסקים מתמידים, נקודה. שנית, `mountPath` הוא `/var/data` בעוד `BACKUP_DIR`
הוא `/var/data/backups` — תת-תיקייה בתוך נקודת העגינה. הקוד יוצר אותה לבד
עם `mkdir(parents=True, exist_ok=True)`.

**וגם עם דיסק מתמיד, הגיבוי עדיין יושב על אותו שירות שהוא מגבה.** אם החשבון
נמחק, אם השירות נמחק בטעות, אם מישהו מוחק את הדיסק — הגיבויים הולכים איתו.
זה מה שהסעיף הבא פותר.

## העותק החיצוני

אחרי כל גיבוי מוצלח, הקובץ מועלה גם לבאקט אחסון אובייקטים (כאן: Cloudflare R2,
שהוא תואם S3). שלוש החלטות עושות את ההבדל בין מימוש שעובד למימוש שמזיק.

**כשל בהעלאה אינו כשל בגיבוי.** ברגע שה-zip נכתב לדיסק, יש לכם גיבוי תקין.
אם R2 לא זמין באותו רגע, זה לא הופך את מה שכבר על הדיסק לפחות תקין:

```python
r2_enabled = r2_backup_enabled()
r2_uploaded = False
if r2_enabled:
    try:
        r2_key = await _upload_backup_to_r2(target_path, filename)
        r2_uploaded = True
    except Exception as exc:
        r2_error = f"העלאה ל-R2 נכשלה: {exc!r}"
        logger.exception(r2_error)
```

התוצאה נשמרת בשדות נפרדים (`r2_uploaded`, `r2_error`) ומוצגת במסך הניהול לצד
סטטוס הריצה. הטעות הנפוצה כאן היא הפוכה בשתי הקצוות: או לסמן את כל הגיבוי
ככושל בגלל תקלת רשת רגעית, או לבלוע את הכשל בשקט. הסימפטום של השנייה: חושבים
שיש עותק חיצוני כבר חודשיים, ואין. הפתרון: כשל שאינו עוצר את הזרימה — אבל
תמיד גלוי במסך.

**באקט נפרד ופרטי.** אם האפליקציה כבר משתמשת ב-S3/R2 לקבצים מצורפים, מפתה
לדחוף את הגיבויים לאותו באקט תחת `backups/`. אל תעשו את זה: באקט הקבצים
המצורפים ציבורי (יש לו `R2_PUBLIC_URL`), וגיבוי שם אומר שמי שמנחש שם קובץ
מוריד את כל המסד. במימוש כאן הבאקט חייב להיות מוגדר במפורש ב-`BACKUP_R2_BUCKET`,
ובלעדיו ההעלאה כבויה — ברירת מחדל שנופלת לצד הבטוח.

זה חייב גם הפרדה בשכבת האחסון: הבדיקה "האם R2 מוגדר" פוצלה לשתיים, כי
`R2_PUBLIC_URL` נדרש למסירה ציבורית של קבצים מצורפים ולא רלוונטי בכלל לגיבוי:

```python
def _has_credentials(settings) -> bool:      # מספיק כדי לפתוח לקוח
    return all([settings.r2_account_id, settings.r2_access_key_id,
                settings.r2_secret_access_key])

def _is_configured(settings) -> bool:        # נדרש רק כשמחזירים URL ציבורי
    return (_has_credentials(settings)
            and bool(settings.r2_bucket_name) and bool(settings.r2_public_url))
```

**רוטציה נפרדת, עם אותם כללי בטיחות.** לעותק החיצוני יש retention משלו — 30 ימים
מול 7 מקומיים, כי זו כל הנקודה שלו. הרוטציה מוחקת רק אובייקטים ששם הקובץ שלהם
תואם את פורמט הגיבוי, ולפי `LastModified` של האובייקט ולא לפי השם:

```python
for obj in objects:
    if not is_safe_backup_filename(obj["key"].rsplit("/", 1)[-1]):
        continue
    if obj["last_modified"] >= cutoff:
        continue
    await r2.delete_object(obj["key"], bucket=settings.backup_r2_bucket)
```

השורה הראשונה היא ההגנה: קוד שמוחק אובייקטים בענן לפי prefix בלבד ימחק גם
קובץ שמישהו הניח שם ביד. והרוטציה רצה רק אחרי העלאה מוצלחת — אותו נימוק כמו
מקומית: לא מוחקים עותקים ישנים כשלא הצלחתם ליצור חדש.

ההעלאה עצמה משתמשת ב-`upload_file` של boto3 ולא ב-`put_object`, כי הראשון קורא
מהדיסק ב-chunks ועובר ל-multipart לבד. ההבדל לא מורגש ב-zip של 5MB; הוא מציל
אתכם כשהמסד גדל והשירות רץ עם 512MB זיכרון.

**להוריד משם** אין endpoint ייעודי — הבאקט פרטי בכוונה. משתמשים בכלי S3:

```bash
rclone copy r2:taskflow-backups/backups/backup_2026-05-03_03-00-15.zip .
# או
aws s3 cp s3://taskflow-backups/backups/backup_2026-05-03_03-00-15.zip . \
  --endpoint-url https://<account_id>.r2.cloudflarestorage.com
```

ומשם — אותו `restore_backup.py` בדיוק.

## API ומסך ניהול

חמישה endpoints, כולם מאחורי אימות (`require_api_auth` שזורק 401):

| Endpoint | תפקיד |
|---|---|
| `GET /admin/backups` | דף HTML לניהול |
| `GET /api/admin/backups` | רשימה + ריצה אחרונה + ריצה הבאה + גודל כולל |
| `POST /api/admin/backups/run` | טריגר ידני (חוסם עד סיום) |
| `GET /api/admin/backups/{filename}/download` | הורדת קובץ |
| `DELETE /api/admin/backups/{filename}` | מחיקה ידנית |

הרעיון החשוב במסך הוא לא רשימת הקבצים — הוא שלוש נקודות המידע שמעליה: האם
המנגנון פעיל, מתי רצה הריצה האחרונה ומה היה מצבה, ומתי הריצה הבאה.
`get_next_run_time()` שולף את זה ישירות מה-scheduler:

```python
def get_next_run_time() -> Optional[str]:
    if _scheduler is None:
        return None
    job = _scheduler.get_job(BACKUP_JOB_ID)
    if job is None or job.next_run_time is None:
        return None
    return job.next_run_time.isoformat()
```

גיבוי שאף אחד לא רואה הוא גיבוי שאף אחד לא מגלה שהפסיק לעבוד. המסך הזה הוא
מנגנון הניטור — הוא לא נועד להיות יפה, הוא נועד לענות על "מתי גובינו לאחרונה"
בשלוש שניות.

(תוצאת הריצה האחרונה נשמרת במשתנה גלובלי בזיכרון, כלומר אחרי restart היא ריקה
עד הגיבוי הבא. מספיק למערכת אישית; אם אתם צריכים היסטוריה אמיתית — כתבו את
תוצאות הריצה ל-collection.)

## אבטחה: שם הקובץ הוא קלט מהמשתמש

`filename` מגיע מה-URL. בלי בדיקה, `GET /api/admin/backups/..%2F..%2Fetc%2Fpasswd/download`
הופך את endpoint ההורדה לקריאה חופשית של מערכת הקבצים. הפתרון פה הוא allowlist
ולא blocklist:

```python
_BACKUP_FILENAME_RE = re.compile(r"^backup_\d{4}-\d{2}-\d{2}_\d{2}-\d{2}-\d{2}\.zip$")

def is_safe_backup_filename(filename: str) -> bool:
    return bool(_BACKUP_FILENAME_RE.match(filename))
```

לא "לחסום `..`" — אלא "לאשר רק מה שנראה בדיוק כמו שם קובץ שאנחנו מייצרים".
כל ניסיון לחסום תווים בעייתיים הוא משחק שאתם מפסידים בו בסוף; regex שמתאר את
הפורמט המדויק מנצח בו תמיד.

אותה פונקציה משרתת גם את `list_backups()`, שמדלגת על כל קובץ שלא תואם. זה מסנן
בדרך גם את קבצי ה-`.partial` — כך שגיבוי שרץ עכשיו לא מופיע ברשימה כאילו הוא מוכן.

## השחזור

הסקריפט הוא `scripts/restore_backup.py`, והוא עומד בפני עצמו: `pymongo` בלבד,
לא מייבא כלום מהאפליקציה, ורץ מכל מחשב שיש לו גישה למסד. זו החלטה מכוונת —
ביום שבו אתם צריכים לשחזר, יש סיכוי טוב שהאפליקציה לא עולה.

```bash
python scripts/restore_backup.py backup_2026-05-03_03-00-15.zip \
  --uri "$MONGODB_URL"
```

שימו לב שה-URI מגיע ממשתנה סביבה ולא נכתב בשורת הפקודה. הוא מכיל את סיסמת
המסד, ושורת פקודה נשמרת בהיסטוריית ה-shell וגלויה לכל מי שמריץ `ps`.

שם מסד היעד נלקח מ-`_meta.json` אלא אם עוקפים עם `--db` — כך ששחזור למסד staging
לצורך בדיקה הוא שינוי של פרמטר אחד.

### שלושת מצבי הכתיבה

זה החלק שבאמת חשוב להבין לפני שמריצים.

`--mode replace` (ברירת מחדל) עושה `drop` ל-collection ואז `insert_many`.
התוצאה זהה בדיוק לגיבוי. **כל מה שנוצר אחרי הגיבוי נמחק.** זה המצב הנכון
לשחזור אמיתי אחרי אובדן, וזה גם המצב שיעלה לכם בנתונים אם תריצו אותו בטעות
על מסד חי.

`--mode upsert` עושה `ReplaceOne` לפי `_id` עם `upsert=True`. מסמכים שקיימים
בגיבוי נדרסים בגרסה מהגיבוי; מסמכים שנוצרו אחרי הגיבוי נשארים. זה המצב לשחזור
נקודתי — "מישהו מחק בטעות 30 משימות אתמול, שאר המערכת תקינה".

`--mode skip` כותב רק ל-collections ריקים. זה המצב למסד חדש לגמרי — מיגרציה
לשרת אחר, הקמת סביבת פיתוח. הוא לא יכול להזיק בהגדרה.

בנוסף יש `--only clients projects` לשחזור חלקי, ו-`--yes` לדילוג על האישור
האינטראקטיבי. אל תשתמשו ב-`--yes` בשחזור ידני. הוא קיים בשביל אוטומציה.

לפני שהסקריפט נוגע במסד הוא מדפיס בדיוק מה עומד לקרות:

```
גיבוי: backup_2026-05-03_03-00-15.zip
  נוצר ב: 2026-05-03T03:00:15+00:00
  מסד מקור: taskflow
  מסד יעד:  taskflow
  מצב:      replace
  collections: 6
    clients: 12 רשומות
    projects: 34 רשומות
    ...

להמשיך? [y/N]
```

ברירת המחדל של האישור היא `N`. Enter בטעות לא מוחק לכם את המסד. זה נשמע קטן
עד הרגע שבו זה מציל אתכם.

### הנוהל שחשוב יותר מהקוד

גיבוי שלא ניסיתם לשחזר הוא לא גיבוי — הוא תקווה. הריצו את התרגיל הזה פעם ברבעון:

1. הורידו את הגיבוי האחרון מ-`/admin/backups`.
2. הרימו Mongo מקומי: `docker run -d -p 27017:27017 mongo:7`
3. שחזרו למסד בדיקה:
   ```bash
   python scripts/restore_backup.py backup_XXX.zip \
     --uri "mongodb://localhost:27017" --db taskflow_drill
   ```
4. הריצו את האפליקציה מולו וודאו שהנתונים נראים נכון.
5. מחקו את המסד המקומי.

חמש דקות ברבעון. הפעם היחידה שבה תגלו שהגיבוי שבור היא הפעם שבה זה לא ישנה.

## מה חסר במימוש הזה

הרשימה הזאת חשובה במיוחד אם אתם מעתיקים את המנגנון לפרויקט חדש — אלה הפערים
שכדאי לסגור מראש.

**העותק החיצוני הוא עותק, לא ארכיון.** הוא מסובב לפי `BACKUP_R2_RETENTION_DAYS`
בדיוק כמו המקומי, רק לאורך יותר. אם מחקו לכם רשומה לפני 45 יום ו-retention הוא
30 — היא איננה בשני המקומות. למי שצריך יותר: הפעילו Object Lock או versioning
ברמת הבאקט, או הוסיפו לרוטציה חריג שמשאיר גיבוי אחד לחודש.

**אין ניטור אקטיבי.** מסך הניהול אומר מה קרה בריצה האחרונה, אבל רק אם נכנסים
אליו. אם הגיבוי מפסיק לרוץ לגמרי — למשל ה-scheduler לא עלה — אף אחד לא יידע.
בפרויקט עם התראות (ל-TaskFlow יש כבר בוט טלגרם) שווה לשלוח הודעה על כישלון.

**הכל בזיכרון.** כל collection נטען לרשימה, מומר למחרוזת אחת, ורק אז נכתב.
צריכת הזיכרון בשיא היא בערך פי שלושה מגודל ה-collection הגדול ביותר. במסד של
עשרות אלפי רשומות זה זניח; במיליוני רשומות תצטרכו לכתוב ל-zip ב-streaming
במקום להרכיב מחרוזת.

**אין snapshot עקבי.** ה-collections נשלפים אחד אחרי השני. אם משתמש יצר משימה
בזמן הגיבוי, ייתכן שהמשימה נכנסה והפרויקט שהיא מפנה אליו לא. בגיבוי לילי של
מערכת אישית זה תיאורטי; במערכת עם תעבורה רציפה שוקלים snapshot ברמת המסד.

**אינדקסים לא מגובים.** רק מסמכים. ב-TaskFlow זה לא בעיה כי `_ensure_indexes()`
רצה בכל עלייה של האפליקציה ויוצרת הכל מחדש. אם בפרויקט שלכם האינדקסים נוצרו
ידנית פעם אחת — הם ייעלמו בשחזור. העבירו אותם לקוד.

**הקובץ לא מוצפן.** zip פשוט. מי שמשיג גישה לדיסק, או ל-session של האדמין,
קורא את כל המסד. אם יש שם מידע רגיש — הצפינו לפני הכתיבה, או לפחות לפני
ההעלאה לאחסון חיצוני.

## צ'קליסט העתקה לפרויקט אחר

הסדר הזה עובד. כל שלב עומד בפני עצמו וניתן לבדיקה.

1. **קונפיגורציה.** הוסיפו ל-Settings: `backup_enabled`, `backup_dir`,
   `backup_retention_days`, `backup_hour`, `backup_minute`.
2. **מודול הגיבוי.** העתיקו את `app/core/backup.py`. התאימו את הייבוא של
   `get_database` ו-`get_settings`. אם אתם על SQL ולא על Mongo — מה שמשתנה זה
   רק `_dump_collection_to_string` (שאילתה במקום `find({})`, `json.dumps` רגיל
   במקום `json_util`); כל השאר — הנעילה, ה-`.partial`, הרוטציה, ה-API — זהה.
3. **תזמון.** הוסיפו APScheduler ל-lifespan עם ההגדרות מהסעיף על תזמון.
4. **אחסון מתמיד.** הגדירו דיסק בפלטפורמה והפנו אליו את `BACKUP_DIR`.
   **בדקו שזה עבד**: הריצו גיבוי ידני, עשו deploy, ובדקו שהקובץ עדיין שם.
   זה הצעד שהכי קל לפספס והכי כואב לגלות מאוחר.
5. **API ומסך.** העתיקו את `app/routers/backups.py` והתאימו את שכבת האימות.
6. **סקריפט השחזור.** העתיקו את `scripts/restore_backup.py` — הוא כמעט גנרי
   לחלוטין.
7. **עותק חיצוני.** באקט S3/R2 ייעודי ופרטי, העלאה אחרי גיבוי מוצלח, רוטציה
   נפרדת. אל תדחו את זה לשלב ב'.
8. **תרגיל שחזור.** לפי הנוהל למעלה, **מהעותק החיצוני** ולא מהמקומי — כך אתם
   בודקים בבת אחת גם את הגיבוי וגם את הדרך להגיע אליו. **לפני** שאתם מסמנים V
   על המשימה.

גיבוי מקומי מגן מפני טעות שלכם; עותק חיצוני מגן מפני אובדן הכל. ותרגיל השחזור
הוא הדבר היחיד ברשימה שמוכיח ששניהם באמת עובדים.
